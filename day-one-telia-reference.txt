SECTION 2 - THE POSTURE - HOW TO APPEAR PROFESSIONAL
================================================================================

The single thing that signals "I've done this before" is COMPOSURE WITH
UNCERTAINTY. New engineers signal newness by either pretending to know
everything or by being visibly anxious. Seniors signal seniority by being
calm about not knowing something specific while clearly being competent.

Three rules:

1. ASK QUESTIONS THAT SHOW STRUCTURE, NOT QUESTIONS THAT SHOW LACK.
   Bad:  "How do I do X?"
   Good: "What's the team's preferred way to do X - I've seen A and B before,
          and want to match how you do it."
   The second shows you have a frame and you're calibrating, not learning
   from zero.

2. WHEN YOU DON'T KNOW SOMETHING, SAY IT CLEANLY. NO HEDGING.
   Bad:  "Yeah, I think I... um, I've kind of done that before..."
   Good: "Haven't used that specific tool before - quick walkthrough would
          help. I'll take notes."
   Senior engineers respect "I don't know yet" infinitely more than fumbled
   pretending. Pretending gets caught immediately and is the fastest way to
   lose credibility.

3. TAKE NOTES VISIBLY. ON PAPER OR IN A NOTEBOOK APP.
   It signals you treat their time as valuable. It also means you don't ask
   the same question twice, which is the second-fastest way to lose
   credibility.

- You can describe what's wrong precisely
- You attempted something before asking
- You have a hypothesis (even if wrong)
- You're asking for confirmation, not rescue

SECTION 7 - SSH KEYS, CREDENTIALS, AND SECRETS
================================================================================

SSH keys are how you authenticate to git servers and remote machines.
Generate them in WSL, not in Windows directly - that way the Linux toolchain
sees them natively.

----- Generate SSH key (Ed25519 - modern, recommended) -----
  $ ssh-keygen -t ed25519 -C "hien.tran.le@telia.com"
  Expected prompts:
    Enter file in which to save the key (/home/hien/.ssh/id_ed25519):
      [press Enter for default]
    Enter passphrase (empty for no passphrase):
      [use a strong passphrase - it's protecting access to internal git]
    Enter same passphrase again:
  Expected output:
    Your identification has been saved in /home/hien/.ssh/id_ed25519
    Your public key has been saved in /home/hien/.ssh/id_ed25519.pub
    The key fingerprint is:
    SHA256:... hien.tran.le@telia.com

----- View the public key (paste into GitLab/Bitbucket/etc) -----
  $ cat ~/.ssh/id_ed25519.pub
  Expected: starts with "ssh-ed25519 AAAA..." and ends with your email

----- Start ssh-agent and add the key (saves typing passphrase repeatedly) -----
  $ eval "$(ssh-agent -s)"
  Expected: Agent pid xxxxx

  $ ssh-add ~/.ssh/id_ed25519
  Expected: prompts for passphrase, then "Identity added"

  $ ssh-add -l
  Expected: shows your key fingerprint and email

----- Test SSH to git server (assuming GitLab) -----
  $ ssh -T git@gitlab.telia.com
       (or whatever the actual hostname is - ASK)
  Expected on success: "Welcome to GitLab, @hien.tran.le!" or similar
  If "Permission denied (publickey)": key not added on the server side yet

----- Check SSH config (~/.ssh/config) -----
  Useful pattern for managing multiple hosts:
  $ cat > ~/.ssh/config <<'EOF'
  Host gitlab.telia.com
      User git
      IdentityFile ~/.ssh/id_ed25519
      IdentitiesOnly yes
  EOF
  $ chmod 600 ~/.ssh/config

----- SECRETS - WHERE THEY BELONG (AND DON'T) -----
  - NEVER commit credentials to git. Period.
  - NEVER store passwords in plain text in your home directory.
  - Use the team's secrets manager (HashiCorp Vault, Azure Key Vault,
    or Telia's equivalent - ASK).
  - Environment variables are fine for short-lived process secrets,
    but treat .env files as sensitive.
  - For Git, use the credential helper:

  $ git config --global credential.helper store
       (stores in ~/.git-credentials - works but plaintext, ask team
        if there's a better option like libsecret or a Windows helper)

  Or for Windows credential integration from WSL:
  $ git config --global credential.helper \
    "/mnt/c/Program\\ Files/Git/mingw64/libexec/git-core/git-credential-manager.exe"

----- GPG (if the team signs commits) -----
  Some teams require GPG-signed commits. Ask.
  $ sudo apt install -y gnupg
  $ gpg --gen-key      (or gpg --full-generate-key for more options)

SECTION 8 - CORPORATE NETWORK - PROXY, CERTIFICATES, VPN
================================================================================

Telia almost certainly has:
- A corporate proxy for outbound HTTP/HTTPS
- An internal certificate authority (CA) - their own root cert
- A VPN for accessing internal resources off the corporate LAN

These are the most common day-one sources of "tools don't work" issues.

----- DETECT PROXY ENVIRONMENT VARIABLES -----
  $ env | grep -i proxy
  If shows entries like:
    http_proxy=http://proxy.telia.com:8080
    https_proxy=http://proxy.telia.com:8080
    no_proxy=localhost,127.0.0.1,.telia.com
  Then proxy is configured. Otherwise, ask if one's needed.

----- SET PROXY VARIABLES (if needed) -----
  Add to ~/.bashrc or ~/.zshrc:
  export http_proxy="http://proxy.telia.com:8080"
  export https_proxy="http://proxy.telia.com:8080"
  export no_proxy="localhost,127.0.0.1,.telia.com,.telia.fi"
  export HTTP_PROXY=$http_proxy
  export HTTPS_PROXY=$https_proxy
  export NO_PROXY=$no_proxy

  Reload:
  $ source ~/.bashrc

----- TEST PROXY -----
  $ curl -v https://www.google.com
  Expected: full handshake, response. If "Could not resolve" -> proxy not
  set correctly. If "SSL certificate problem" -> see CA section below.

----- TRUST THE CORPORATE ROOT CA -----
  Telia's internal services use internal CA-signed certificates. Your
  laptop trusts these out of the box because of Windows policy, but WSL
  and tools like curl, pip, npm DON'T automatically inherit this trust.

  Symptom of missing trust:
    curl -v https://internal-tool.telia.fi
    -> "SSL certificate problem: unable to get local issuer certificate"

  Fix - get the corporate root CA cert (ASK for the file - probably .crt
  or .pem format) and install it system-wide:

  $ sudo cp telia-root-ca.crt /usr/local/share/ca-certificates/
  $ sudo update-ca-certificates
  Expected: "1 added, 0 removed; done."

  Verify:
  $ curl -v https://internal-tool.telia.fi
  Should now succeed.

  PYTHON specifically may need its own CA bundle:
  $ pip install certifi
  $ python3 -c "import certifi; print(certifi.where())"
  -> shows path to cacert.pem
  Then append the Telia root CA to that file or set:
  $ export REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt
  $ export SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt

  NPM:
  $ npm config set cafile /etc/ssl/certs/ca-certificates.crt

  GIT:
  $ git config --global http.sslCAInfo /etc/ssl/certs/ca-certificates.crt

----- VPN CHECK -----
  Telia likely uses one of: Cisco AnyConnect, GlobalProtect, Zscaler.
  These run on Windows and tunnel before WSL sees the network.

  $ ip route
  Look for routes that suggest VPN is active (often a tun0 interface
  on the Windows side, but WSL2 sees it as transparent eth0).

  Test internal hostname:
  $ curl -v https://intranet.telia.com    (or whatever you're given)
  If hangs or fails -> VPN probably down or not connected.

----- DNS CHECK -----
  $ cat /etc/resolv.conf
  Expected: nameserver entries pointing to corporate DNS once VPN is up

  $ nslookup zaara-fi-instance-01.telia.fi    (or whatever)
  Expected: resolution to an internal IP. Tests both DNS and VPN.

----- PORT CHECK FROM WSL -----
  $ nc -zv internal-host 443
  or
  $ curl -v telnet://internal-host:443
  Useful for testing whether a specific port is reachable through the
  corporate network.

SECTION 11 - WHAT THE SENIOR SHOULDN'T HAVE TO TELL YOU
================================================================================

Background knowledge - don't make him explain these. If he asks if you
know any of these, a brief "yes, used it before for X" is fine.

----- BASIC LINUX FILE PERMISSIONS -----
  ls -l                            (read permissions string: drwxr-xr-x)
  chmod 600 file                   (owner read/write only - for SSH keys)
  chmod 755 script.sh              (owner all, group/others read+exec)
  chown user:group file
  sudo                             (run as root - sparingly)

----- BASIC NAVIGATION -----
  cd, ls, pwd, mkdir, rm, cp, mv, ln -s
  find /path -name "*.log"
  grep -r "pattern" /path
  cat, less, head, tail
  tail -f /var/log/something.log   (follow a log live)

----- BASH BASICS -----
  $variable
  export FOO=bar
  cmd1 | cmd2                      (pipe)
  cmd > file                       (redirect stdout)
  cmd 2> file                      (redirect stderr)
  cmd1 && cmd2                     (run cmd2 only if cmd1 succeeds)
  cmd1 || cmd2                     (run cmd2 only if cmd1 fails)

----- PROCESS BASICS -----
  ps aux | grep something          (find a process)
  top, htop                        (live process viewer)
  kill <pid>                       (signal a process)
  systemctl status servicename     (check a systemd service)
  journalctl -u servicename -f     (follow a service's logs)

----- BASIC NETWORK INVESTIGATION -----
  curl -v url                      (with verbose, see headers)
  curl -k url                      (skip TLS verification - DEBUG only)
  ss -tlnp                         (sockets listening + processes)
  netstat -tlnp                    (older alternative)
  dig hostname                     (DNS query)
  nslookup hostname                (DNS query, simpler output)
  ping host
  traceroute host
  nc -zv host port                 (test if port is reachable)

----- GIT BASICS -----
  git clone url
  git status
  git pull
  git checkout -b feature/branch-name
  git add -p                       (stage selectively, interactive)
  git commit -m "message"
  git push -u origin branch-name
  git log --oneline -20

----- THE CHECK-EVERYTHING DISCIPLINE -----
  After setup, before declaring done:
  - Can I clone an internal git repo?
  - Can I push back?
  - Can I curl a Telia internal URL successfully?
  - Can I resolve internal DNS names?
  - Do my IDE, terminal, and WSL all see the same git config?
  - Did I lock my laptop when I went for coffee?

SECTION 13 - THE MENTAL DISCIPLINE - DON'T FORGET THESE
================================================================================

Things to remember even when tired:

- It's okay to take 3-5 days to be fully productive. Everyone knows this.
  Don't push for "useful today" - push for "set up properly."

- Listen 70%, talk 30% on day one. The senior knows things you don't yet
  know you need to know.

- When the senior corrects you, say "good catch" or "thanks - noted" -
  don't apologize repeatedly. Apologies pile up; corrections move on.

- If you make a mistake (broke something, ran the wrong command), say
  it immediately and clearly. Don't try to fix it silently. Senior
  engineers respect "I just ran X and it errored - I'll back out and
  ask before retrying" enormously.

- DO NOT touch production systems on day one. Even if you have access.
  Even if you're sure. Read-only is the only mode for week one.

- DO NOT install random software from random sources. Stick to what the
  team approves. The corporate image is curated for a reason.

- DO NOT bypass anything that looks like a security control. If
  something doesn't work because of a cert/proxy/policy, the fix is to
  request the right access, not to work around the restriction.

- DO NOT share credentials or tokens through chat/email/screenshots.
  Use the team's secret-sharing pattern (Vault, 1Password Teams,
  whatever they use). If unclear, ask before sharing.

- Lock your laptop every time you leave the desk. Win+L.

- Take breaks. Setup days are draining. A 10-minute walk between
  install/permission/install/permission cycles keeps your judgment
  sharp.

SECTION 15 - EMERGENCY POCKETS - IF THINGS GO WRONG
================================================================================

If laptop won't boot:
- Don't panic. Try the corporate IT support line first.
- Note exactly what's on screen.

If WSL won't install:
- Probably needs admin rights or Hyper-V enabled.
- "wsl --install" often fails on locked-down images; the senior may
  need to enable Windows features for you.
- Don't fight it - escalate via the right path.

If you can't reach an internal site:
- Check VPN connection first (corporate VPN app)
- Check DNS resolution (nslookup)
- Check certificate trust (curl -v shows the error)
- Check proxy settings (env | grep -i proxy)

If credentials don't work:
- Don't retry many times - account lockout is real, often 3-5 failed
  attempts.
- After 2 failures, stop and ask.

If you accidentally do something potentially serious:
- Stop immediately. Don't try to fix it alone.
- Tell the senior immediately. The earlier you escalate, the less
  damage and the more credit for honesty.

SECTION 16 - FINAL THOUGHTS
================================================================================

Tomorrow isn't about impressing anyone with technical skills. The senior
is not auditioning you on bash commands or Linux trivia. He's reading
two things:

1. Are you organized and curious?  Do you take notes, ask sharp questions,
   verify things work end-to-end, document what you do?

2. Can you handle uncertainty gracefully?  Tomorrow will involve waiting
   for provisioning, working around blockers, and not-yet-knowing the
   answer to things. The senior wants to see you stay productive and
   composed when not everything works on the first try.

If you nail those two, the technical mastery comes naturally over the
weeks. The credibility from day one comes from posture and approach.

The single best move you can make all day, when you don't know
something: pause, look at him, and say:

  "Walk me through that - I want to get it right."

That sentence, used at the right moments, is the difference between
"new hire who's learning" and "professional who's calibrating."
