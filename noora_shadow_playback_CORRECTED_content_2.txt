SLIDE 3 — About Noora
Noora is a highly customized system, originally created for IP Backbone monitoring in
Finland using SevOne NMS as its core. It has many custom components and automated
functions layered on top, making it effectively a separate system that uses SevOne NMS
as one component.

Monitoring Capabilities
Noora monitors Finnish Inter-Regional, Regional, and Local-Aggregation networks, as
well as SD-WAN platforms. It also collects service-related data from TV, SDN, 3G, 4G,
and 5G services, including network cross points.

Users of Noora
- SA Organization Units: network surveillance and threshold-based alarm handling for Finnish IP Backbone devices
- Operational Network Teams: graphical user interfaces for real-time troubleshooting and data analysis
- Business and Planning Units: performance data, reporting structures and statistical data for the Qlik system; network planning and build costs are calculated/predicted from Noora's data

SLIDE 18B — NEW — Data Retention, Rollups & Capacity Planning
Retention
- Raw statistics retained 240 days in SevOne's DATA database
- Horizon transport-data retention is also configured for 240 days - only ~6 months of history has accumulated so far, so the full 240-day window hasn't actually been tested yet
- No retention issues encountered so far; capacity planners would be the ones to flag it if they couldn't get the history they needed

Rollups / older data
- For data older than ~30 days, SevOne uses "Synthetic Indicators" (Object Types -> Interface -> Edit -> Synthetic Indicator) to aggregate/calculate from underlying sources - marked in the UI with a synthetic-indicator icon
- The exact rollup/retention value isn't easily visible in the UI itself - consult the SevOne manual if it's ever in question

Capacity planning
- Capacity is licensed per active object; watch the trend per peer, not just the snapshot (~1%/day growth is a flag, ~0.5%/day is already worth noting)
- Must stay well under 95%; SevOne stops polling entirely if a peer hits 100% (devices stay provisioned but simply don't get polled)
- When capacity got close to 100% previously, Kurt made rulebook changes (disabling certain objects, per the rulebook, in consultation with Telia) that brought it back under 80% within weeks
- Longer-term planned fix is adding another poller appliance ("a 10th aura") to redistribute load - currently a frozen/on-hold plan, not actively in progress
- No pressure or complaints so far about Noora's overall storage footprint

SLIDE 19C — NEW — Known Issues & Recurring Fixes (Quick Reference)
1. Broken / duplicate links
   - Symptom: link/device shows as missing or duplicated in Object Manager
   - Fix: identify the "deleted_"-flagged vs. active copy in Object Manager, check history/expression in the Calculation Editor, remove the "deleted_" flag and re-provision (or delete the duplicate) depending on whether history needs preserving
   - Reported by: Juho Kontio, Rami Kivirinta (via shared mailbox); usually resolved within 1-2 days once Kurt runs a port check

2. Tomaatti CSV formatting errors
   - Symptom: External Data tab shows red on Data Parsing; Provisioning Control backs up with climbing device count
   - Fix: SSH to ferguson, locate the CSV under /opt/provisioning/dump/, fix the malformed line (e.g. a stray blank line) directly, confirm Data Parsing goes green again, then click Auto Update in Provisioning Control to confirm the backlog is clearing

3. "No XML document" / control-character device errors
   - Symptom: SOAP/API calls fail for a device (a known SevOne bug where a control character gets saved into the database)
   - Fix: low-frequency issue; sometimes resolved by a full device reboot; Kurt/IBM are aware; check the Device Dashboard first for this class of error

4. Missing chassis / hardware inventory data
   - Symptom: a device shows as working but its hardware/chassis inventory is missing (affects spare-part/cost reports)
   - Status: in active investigation with Kurt; working theory is SAP not providing the chassis inventory info; check pinning logs and the relevant PHP report

5. Wrong generic device role from SM/O (large-scale)
   - Symptom: 100+ devices duplicated across many rings after an SM/O bug tagged the wrong device role
   - Fix: manual triage, historically took several weeks; now caught earlier via the tightened weekly Change Report review

6. Stuck device at provisioning phase 2
   - Fix: if a normal re-provision doesn't clear it, delete the device from Device Discovery and trigger a fresh discovery - this has unstuck cases where the device wasn't going through SevOne discovery correctly, without affecting the working device

This protocol covers the daily health check across Noora's own stack: the application
server, SevOne NMS, Rasmus, Rasmus Admin, and the Noora Health Portal. Checking the

- Login: TCAD ID + Veha LDAP password
- Check peers (ferguson + the aura0x pooler appliances); Total License Consumption is the key figure to watch - should never reach 100% (polling stops); stay well under 95%
- Watch the trend, not just the snapshot: growth of ~1%/day is a flag, ~0.5%/day is already worth noting
- aura07 runs deliberately low (dedicated to a specific device type)

3. SevOne NMS - Alarms / Alerts
- Log in/out to check admin messages are still clearing normally
- Check alerts are flowing in; compare the latest alert's timestamp to system time; confirm filters are correct
- ~330 alerts is typical for SevOne NMS; if it jumps drastically toward ~600, contact the Resource Manager
- 15 minutes with no alerts at all would be abnormal
