NOORA KNOWLEDGE TRANSFER - COMPREHENSIVE ANSWERS
===================================================

This document provides detailed answers to all Noora knowledge transfer questions
based on the extracted documentation, KT session notes, and system information.

=== SYSTEM OVERVIEW ===

Q1. What is Noora and its relationship to SevOne?
A1. Noora is a customized network monitoring system built on top of SevOne NMS (Network Management System).
   - SevOne NMS is a commercial all-in-one network performance monitoring product
   - Custom components were built to extend SevOne's capabilities
   - These components + SevOne NMS form the system called Noora
   - Noora includes: data gathering/organization, automated provisioning, monitoring/alert management, report management/data export
   - Tailored reporting UIs provide easier access to statistical data
   (Reference: noora_system.txt Slide 2, noora_system_what_is_monitored_1.png)

Q2. What is the current scope of Noora monitoring?
A2. Noora monitors a comprehensive range of network components:
   - Fixed network monitoring (IP backbone, mobile CORE)
   - Broadband, mobile, and telco EDGE networks
   - Regional networks (Metro Ethernet)
   - NFVI/SDN/Virtual monitoring (Virtual EDGE, SD-WAN, Hyperscale nodes)
   - Special monitoring (B2C IP allocation, Hybrid Access, Cable HFC RF signals)
   - Capacity reporting for infrastructure management
   - Traffic monitoring (Peering, NNI, Core, Edge, Metro, Service-based traffic)
   (Reference: noora_system.txt Slide 3)

Q3. What are the main components of Noora architecture?
A3. Noora architecture consists of:
   - SevOne NMS (core monitoring engine)
   - Noora engine (custom processing)
   - Noora data handling (input/output processing)
   - Input data feeds (SNET, SMO, SAP, etc.)
   - Noora custom UIs (System management, Report management, Custom Statistics)
   - External output data (Alert reporting, Capacity reporting, Realtime reporting)
   (Reference: noora_system.txt Slide 4)

=== DEVICE AND MONITORING MANAGEMENT ===

Q4. What types of devices and components does Noora monitor?
A4. Noora monitors comprehensive device components:
   - Device performance statistics (CPU, memory, hardware status)
   - Physical interfaces (Copper, fiber, coaxial, wireless - traffic, drops, errors)
   - Logical interfaces (Aggregated, subinterfaces, virtual interfaces)
   - Class of Service (CoS) monitoring
   - Inventory information (Serial numbers, part numbers, etc.)
   (Reference: noora_system.txt Slide 5, noora_system_what_is_monitored_1.png)

Q5. How does Noora handle device polling and data collection?
A5. Noora's data collection process:
   - Devices are polled every 180 seconds (3 minutes)
   - Polled data is immediately available in the system
   - Raw data retention: 240 days
   - Data is stored in two databases:
     * CONFIG database: Configuration and metadata (replicated)
     * DATA database: Raw statistics (unique per server/appliance)
   - System stores ~2.7M values per 180-second interval
   (Reference: noora_system.txt Slides 6, 9)

Q6. What is Noora's licensing model?
A6. Noora licensing is based on:
   - Number of active objects (not devices)
   - Current system: ~4k network devices, ~120k objects, ~2.7M indicators
   - Approximate license cost: ~1.2€ per object
   - Objects include: interfaces, CPU, memory, CoS queues, etc.
   (Reference: noora_system.txt Slide 8)

Q7. How does Noora handle device grouping and organization?
A7. Noora uses sophisticated grouping mechanisms:
   - Device groups: Collections of devices bound by common factors
   - Object groups: Collections of objects (interfaces, CPU, etc.)
   - Groups are used for:
     * User privilege management
     * Alert policy bindings
     * Report generation
     * Creating additional groups
   - Metadata can be set as groups
   - All groups are searchable via Noora reporting UIs
   - Automatic grouping rules (e.g., "metro" in name → Metro group)
   (Reference: noora_system.txt Slides 12-14)

=== REPORTING AND DATA MANAGEMENT ===

Q8. What reporting systems does Noora provide?
A8. Noora offers multiple reporting systems:
   
   A. Noora Reporting (for Service Assurance):
   - Designed for real-time service assurance
   - Raw data available immediately after polling
   - Accessible via:
     * Rasmus Reporting System (Device/Interface dashboards, Group reporting)
     * Horizon Reporting System (Statistics)
     * SMO Embedded Graphs (Static dashboards)
   - Data retention: 240 days raw data
   
   B. Qlik Reporting (for Planning and Business):
   - Designed for long-term planning and business reporting
   - Uses 24-hour average and max data
   - Data preparation process:
     * Device validation and enrichment (Noora Engine)
     * Reporting structure management (Rasmus Admin)
     * Report data selection automation
     * Data summary calculations
   - Available through QlikView and QlikSense dashboards
   - Drill-down details available via Noora reporting UIs
   (Reference: noora_system.txt Slides 6-7, multiple Qlik reporting images)

Q9. How does Noora handle data flow and automation?
A9. Noora's automated data flow includes:
   - Input data collection from multiple sources (SNET, SMO, SAP, etc.)
   - Automatic statistic data collection and categorization
   - Automated data enrichment and provisioning
   - Alert policy and report management automation
   - Example automated processes:
     * Device provisioning when added to OSS system
     * Group creation and updates
     * Alert policy binding based on device/object characteristics
     * Report generation and scheduling
   - Full automation from user perspective (5-15 minute processing)
   (Reference: noora_system.txt Slides 15-16, Data_flow_Automation images)

=== ALERT AND INCIDENT MANAGEMENT ===

Q10. How does Noora handle alert management?
A10. Noora's alert management system:

     * Target: Mobile & CPU, Trigger: CPU Load >95%, Action: Critical alert
   - Alerts are automatically generated and sent to appropriate systems
   - Alert documentation available in NetDoc wiki
   (Reference: noora_system.txt Slide 15, kt2_noora_final.txt)

A11. Incident management process:

   - Rule of thumb: Look up systems in CMDB for relevant contacts
   (Reference: kt1_noora_final.txt, kt2_noora_final.txt)

=== TECHNICAL DETAILS ===

Q20. What is the SevOne cluster setup?
A20. Cluster architecture:
   - Master and collector servers/appliances can be separated
   - Can use physical servers or virtual appliances
   - Statistical data (DATA database) is unique per server
   - Configuration data (CONFIG database) is replicated
   - Allows easy scaling of the system
   - Security zones can separate different components
   (Reference: noora_system.txt Slide 10)

Q21. How does metadata enrichment work?
A21. Metadata processing:
   - Metadata refers to bindable data related to devices/objects
   - Parsed from different source inventories
   - Bound to target devices/objects during provisioning
   - Includes: Name, description, IP address, SNMP community, location, etc.
   - For interfaces: Speed, connected device/port information
   - For hardware: Serial numbers, product names, manufacturers
   - Metadata parsing and storage are scripted and automated
   (Reference: noora_system.txt Slide 11)

Q22. What are the key differences between Noora and standard SevOne?
A22. Noora vs. SevOne differences:
   - Custom components for data gathering and organization
   - Automated device provisioning workflows
   - Enhanced alert management automation
   - Advanced report management and data export
   - Tailored reporting UIs for easier access
   - Custom environment management
   - Integration with Telia-specific systems (SNET, SMO, SAP)
   - Extended data retention and processing capabilities
   (Reference: noora_system.txt Slide 2)

=== ALERTS AND THEIR BUSINESS IMPACTS ===

Q1. What are the most important alerts and their business impacts?
A1. The most important alerts include:
   - Monitoring emails
   - Ferguson server alerts
   - Nelli Pulse notifications
   - Email notifications from scripts
   - Fatal errors identified during Daily Health Checks (DHC)
   
   Business impacts:
   - Monitoring emails ensure timely communication of issues.
   - Ferguson server alerts indicate potential provisioning failures.
   - Nelli Pulse notifications provide real-time incident updates.
   - Script notifications highlight automation or integration issues.
   - Fatal errors in DHC indicate critical system failures requiring immediate attention.

Q2. How do you determine whether an alert is actionable or informational?
A2. Alerts are evaluated based on:
   - Root Cause Analysis (RCA)
   - Basic evaluation of the incident or situation
   - Impact on system performance and user experience
   - Urgency and severity of the issue

Q3. What are the common issues encountered?
A3. Common issues include:
   - Integration challenges
   - Data collection and provisioning errors
   - Alert configuration and delivery problems
   - System performance and capacity concerns

=== DAILY HEALTH CHECK PROCEDURES ===

Q4. Which dashboard is reviewed first during the Daily Health Check (DHC)?
A4. The order of dashboard reviews during DHC can be adjusted based on priorities. Key dashboards include:
   - Noora Health Portal
   - Ferguson server status
   - Alert and notification logs
   - System performance metrics

Q5. What troubleshooting steps are typically performed for data collection issues?
A5. Troubleshooting steps for data collection issues:
   - Check external data sources (e.g., SMO data)
   - Verify SevOne polling status
   - Ensure XML configurations are correct
   - Enable object monitoring if disabled
   - Loop in relevant personnel (e.g., Kurt) for further investigation

=== PLATFORM HEALTH AND KPIs ===

Q6. What KPIs are considered most critical for platform health?
A6. Critical KPIs for platform health include:
   - License numbers and capacity usage
   - System performance metrics (CPU, memory, disk utilization)
   - Data collection and polling status
   - Alert and notification delivery success rates
   - Integration and external data flow status

Platform Health Checklist:
   1. Platform Health:
      - Verify all NMS and data insight components are operational.
      - Follow DHC protocols for comprehensive checks.
   
   2. Active or Critical Alerts:
      - Monitor device alerts sent to Nelli.
      - Address critical alerts promptly.
   
   3. Polling Functionality:
      - Check device configuration for polling status.
      - Identify unsupported devices without XML documents.
      - Use System Tools => Device Deviation for troubleshooting.
      - Note: Polling can be manually disabled for devices with high object counts (e.g., 8000 objects).
   
   4. Packet Loss or Collection Delay:
      - Check for packet loss using SevOne tools.
      - Use Rasmus and Horizon for detailed analysis.
      - Monitor Noora Health => Device Dashboard => Package Loss.
   
   5. Cluster Instance Synchronization:
      - Verify cluster manager status (not typically checked in DHC).
      - Ensure poller server is operational (green status).
      - Confirm Ferguson server status.
